# Working in Cairn

- **Performance gates override the standing auto-merge authorization below.** Every PR must report baseline, previous `main`, and current PR performance in its description or linked comment. Identify immutable revisions, matched device/OS/profile, scenarios, evidence and verdict. Run the existing simulated power/rendering regression checks on every PR; they are not hardware energy measurements. Use `scripts/battery_benchmark.py` and `docs/BATTERY-VALIDATION.md`.
- **A full physical-phone matrix is not required on every PR.** Establish it initially per device/OS/profile. Reuse measured scenario evidence only after a documented diff-based impact review shows its measured execution paths and conditions are unchanged; identify the original measured revision and explicitly label the current entry as reused, not newly measured. For changes to GPS requests, recording/service lifecycle, timers/wake locks, rendering/tile loading, background network/storage or relevant dependencies, remeasure affected phone scenarios and retain valid unaffected evidence. If scope is uncertain, require fresh affected measurements. Recheck the full matrix for a power-affecting release or a change of device, OS, measurement setup or power policy. No blanket exemption based on PR size or file extension.
- **Do not enable or leave native auto-merge enabled when performance is worse than baseline or previous main, an objective fails, or required evidence is missing, stale or inconclusive.** A documented, valid reuse decision satisfies the evidence requirement; simulation alone cannot establish a hardware baseline. Do not silently lower the baseline or manually merge to bypass the gate. Baseline changes require an explicit owner decision with old/proposed results visible. The initial unmeasured baseline does not authorize auto-merge, including for this PR.
- **Standing user authorization for every PR and every agent:** The repository owner explicitly authorizes all current and future agents working on `cairn-map/android` to enable GitHub's native auto-merge on every ready-for-review PR, including the PR that records this authorization. This includes the eventual merge into `main` and the normal merge-triggered release workflow after GitHub's required checks and branch protections pass. No separate per-PR user confirmation is required. This records the owner's instruction on 2026-10-22: "Make sure every PR and every future agent has the right to enable auto-merge." A later explicit user instruction to keep a PR draft, open or manually merged takes precedence.
- Enable native auto-merge separately for each ready-for-review PR; the repository setting alone does not enable it for individual PRs. It is authorized to queue auto-merge while required checks are pending: GitHub must wait for them to pass. This authorization never permits bypassing failed, pending or stale checks, unresolved review conversations, branch protections, signing verification or a tool-level approval rejection. Report a tool-level approval rejection accurately; do not describe it as a GitHub rule or invent a new user-approval requirement when the tool has not imposed one.
- Deliver repository changes through a pull request against `main`. Create a descriptive feature branch, commit and push the changes, open a ready-for-review PR, and include its URL in the final response. Do not leave completed work only in the local workspace or push source changes directly to `main`.
- Use a specific, user-facing PR title: GitHub automatically turns merged PR titles into changelog entries in Releases. Describe the user-visible behavior and relevant validation in the PR. Run `bash gradlew assembleDebug testDebugUnitTest lintDebug --console=plain --max-workers=2`, `python3 -m unittest discover -s scripts -p 'test_*.py'`, `node --test scripts/test-*.cjs`, and `actionlint` when changing workflows. PR CI always runs Android build/tests/lint and pinned actionlint; Python and bounded Node automation suites run only for automation, workflow, signing-policy or build-configuration changes. Unknown change history runs both suites. Use the shared selector in `scripts/automation_changes.py` for PR and release decisions.
- GitHub's **native auto-merge** is opt-in for each pull request, and the `checks` job from **Android checks** is a required strict status check in the `main` ruleset. The repository and `main` ruleset must permit **merge commits only** (disable squash and rebase), because release validation reuse requires a two-parent merge commit. The repository has one maintainer, @dayblox: require **zero** PR approvals, and **do not** require code-owner approval or last-push approval, since a PR author cannot self-approve. Inspect the whole PR diff before enabling auto-merge, with particular care for `.github`, release automation, signing or build infrastructure; the standing authorization also applies to these PRs. Open a ready-for-review PR and enable native auto-merge with `gh pr merge --auto --merge` or GitHub's auto-merge control after checking the repository merge settings. Leave auto-merge off when the user explicitly requests manual review or merging for that PR. Never bypass failed, pending or stale checks. Draft PRs are intentionally not auto-merged.
- If native auto-merge is unavailable unexpectedly, leave the PR open and report the blocker; do not bypass branch rules. A deliberate manual merge for a sensitive PR is allowed only after all required checks pass. An administrator can verify the repository configuration with `python3 scripts/configure_native_automerge.py --dry-run` and apply it using the same command without `--dry-run`.
- GitHub merges PRs after requirements pass, triggering the existing `push` release workflow. Merge-generated releases can perform full validation when no trusted PR validation run ID was supplied. Release versions and Android version codes advance automatically; never replace a published release or release a source that does not contain the latest published source.
- PR checks must always run the Android build, tests and lint before recording validation evidence, plus automation suites when the shared change selector requires them. Release reuse requires verified evidence for the identical merged tree and toolchain; preserve Android full-validation fallback for missing/mismatched evidence and CI/script changes. Release fallback runs automation suites for relevant changes or unknown history, including manual dispatch; an image mismatch alone does not require rerunning unchanged automation. Never bypass APK signing or release verification.
- Keep signing keys and passwords out of Git, logs, PRs and release assets. CI uses GitHub Actions secrets and verifies the key against `release-signing.sha256`. Reuse the existing key; replace it only with explicit user authorization because Android cannot update an app signed by a different key.
- GitHub's **Automatically delete head branches** repository setting cleans up merged feature branches. Preserve branches containing unmerged work.
